## Erledigt
- [Hoch] Custom Workout mit "mit Warmup" wird nicht gespeichert (ursprünglich gemeldet: Klick auf "Start" mit Warmup sendet keinen Insert, "Eigene Workouts"-Zähler blieb bei 11) — **auf `carveout.app` live nachgestellt, reproduziert nicht mehr**: kompletter Wizard-Flow (AMRAP, Name, "Ja, Warmup", Start) hat sauber inserted, Zähler 11→12, Testeintrag anschließend wieder gelöscht. Vermutlich bereits durch Commit `1779794` ("warmup for saved workouts", 2026-06-05) oder `dfc840b` behoben, nur nie in BUGS.md nachgetragen. War nur ein Doku-Rückstand, kein neuer Fix nötig.
- [Hoch] History-Tab lädt endlos ("Loading history..." dauerhaft, nie ein Request an wod_history) — **auf `carveout.app` live nachgestellt, reproduziert nicht mehr**: sowohl der History-Tab in `/workout` als auch die eigenständige `/history`-Route laden Einträge sofort und korrekt. Vermutlich bereits durch Commit `dfc840b` ("History-Bug", 2026-05-31) behoben, nur nie in BUGS.md nachgetragen. War nur ein Doku-Rückstand, kein neuer Fix nötig.
- [Hoch] Inkonsistente Filter-Trefferzahlen bei Programm-Filtern (156/30/416 bei "Kraft - Wenig Zeit") — Root Cause: `useWods.ts` racet die Supabase-Query gegen ein 5s-Timeout; verliert die Query, fiel der Code still auf den lokalen `wods.json`-Fallback zurück, der `wodCategory` komplett ignoriert (diese WODs existieren nur in Supabase) → mal korrekte, mal stark abweichende Zahl. Fix: Timeout auf 8s angehoben; bei `forceSupabase`-Filtern (wodCategory/editorsPick) wirft die Query jetzt bei Timeout/Fehler einen Error statt still auf falsche lokale Daten umzuschalten — `WodList` zeigt dafür den vorhandenen Fehlerzustand ("WODs konnten nicht geladen werden"). Verifiziert: 3× Reload mit identischem Filter → konsistent "30 Workouts", kein Fallback mehr.
- [Hoch] Main-Thread-Freeze bei Workout-Detail (schwarzer "Loading…"-Screen, wirkte wie CPU-Freeze) — **Korrektur:** Die ursprüngliche Einschätzung in diesem Bug-Eintrag ("konnte NICHT reproduziert werden, vermutlich Testinfrastruktur-Artefakt") war falsch. Am 2026-08-19 live auf `carveout.app` reproduziert (erst durch Tim/Cowork, dann durch Claude Code via Claude-in-Chrome). Root Cause: kein CPU-Block (trivialer JS-Eval lief währenddessen sofort durch) — stattdessen ein dauerhaft gehaltenes exklusives `navigator.locks`-Lock (`lock:sb-<ref>-auth-token`, supabase-js' Cross-Tab-Auth-Lock): ein anderer offener Tab hatte seinen `getSession()`-Call nie beendet und das Lock nie freigegeben; `authStore.initialize()` wartete ohne Timeout auf `getSession()` → `loading` blieb für jeden neuen Tab/Reload für immer `true`, `ProtectedLayout` zeigte endlos "Loading…". Erklärt den beobachteten Workaround "PWA-Neuinstallation aufs Handy hilft" (killt alte Tab-Kontexte, die das Lock halten). Fix: `getSession()` racet jetzt gegen 8s-Timeout, `loading` wird bei Timeout trotzdem auf `false` gesetzt; `onAuthStateChange`-Listener wird unconditional registriert. Commit `c45da68`.
